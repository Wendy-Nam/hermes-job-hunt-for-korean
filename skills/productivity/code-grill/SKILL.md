# Code Grill

## Overview

구현 전에 계획, 설계, 기능 방향을 빡세게 털어보는 스킬이야. 목표는 USER 의견에 무조건 맞장구치는 게 아니라, 나중에 비싸게 터질 결정을 지금 싸게 드러내는 거야.

항상 **한 번에 한 질문**만 한다. 질문은 날카롭게, 하지만 막연하게 몰아붙이지 않는다. 가능한 답은 내가 먼저 코드베이스나 파일을 뒤져서 찾고, 그래도 결정이 필요하면 USER한테 묻는다. 매 질문마다 **추천 답안**을 같이 제시하고, USER 피드백을 받은 뒤 다음 질문으로 넘어간다.

## When to Use

- PRD 쓰기 전에 핵심 가정이 맞는지 검증해야 할 때
- 기능 구현 전에 범위, 데이터 모델, API, UX 흐름을 먼저 압박해봐야 할 때
- 여러 설계 결정이 서로 물려 있어서 하나 틀리면 연쇄로 흔들릴 때
- 데이터 모델, 이벤트 스키마, API 계약, 권한 모델을 확정하기 직전
- “그냥 만들어줘”보다 “반박하고 물고 늘어져줘”가 필요한 때
- 기존 코드베이스와 새 방향이 충돌할 가능성이 있을 때
- 마이그레이션, 호환성, 롤백, 관측성 같은 뒷감당이 큰 작업 전

Don't use for:

- 이미 작은 버그 수정처럼 해법이 명확하고 리스크가 낮은 작업
- USER이 명시적으로 “질문하지 말고 바로 구현해”라고 한 경우
- 단순 문서 정리나 포맷팅처럼 설계 결정이 거의 없는 작업

## Workflow

### 1. Grill 모드 선언

시작할 때 짧게 선언해.

- “좋아, 바로 구현 안 하고 먼저 grill 할게.”
- “한 번에 한 질문만 던질게. 내가 추천 답도 같이 줄게.”
- “코드에서 확인 가능한 건 먼저 뒤져보고, 결정이 필요한 것만 물어볼게.”

Completion criterion: USER이 지금은 구현보다 검증 루프라는 걸 알 수 있어야 한다.

### 2. 입력을 쪼개서 위험 지도를 만든다

사용자 설명, PRD 초안, 이슈, 코드 조각, 파일 경로를 읽고 다음을 분리해.

- 목표: 진짜로 만들려는 결과가 뭐야?
- 사용자/호출자: 누가 쓰고, 어떤 권한으로 쓰지?
- 현재 시스템: 이미 있는 모델, API, 패턴, 제약은 뭐야?
- 결정 후보: 아직 확정 안 된 선택지는 뭐야?
- 실패 비용: 틀리면 나중에 어떤 비용이 생기지?

Completion criterion: 첫 질문을 고를 만큼 리스크 우선순위가 잡혀 있어야 한다.

### 3. 코드베이스 먼저 뒤진다

질문하기 전에 확인 가능한 건 직접 확인해.

- 관련 파일, 라우트, 모델, 스키마, 테스트, 문서 검색
- 비슷한 기능의 기존 패턴 확인
- 타입/DB/API 경계 확인
- 마이그레이션, feature flag, config, permission 패턴 확인
- 최근 변경이나 TODO가 영향을 주는지 확인

확인한 내용은 짧게 근거로 붙여.

> “코드 보니까 기존 결제 플로우는 `Order.status`를 단일 source of truth로 쓰고 있어. 그래서 첫 질문은 이거야…”

Completion criterion: 물어볼 질문이 “내가 찾을 수 없어서 묻는 것”인지, “USER 결정이 필요해서 묻는 것”인지 구분되어야 한다.

### 4. 한 번에 한 질문만 던진다

형식은 이 패턴을 지켜.

```md
질문 1 — <짧고 날카로운 질문>

왜 묻냐면: <이 결정이 뒤에 미치는 영향>

내 추천: <추천 답안. 가능하면 구체적으로>

USER 답: A/B/C 중 고르거나, 수정해서 말해줘. 답 주면 다음 질문으로 갈게.
```

규칙:

- 질문은 하나만. 여러 개 묶지 마.
- 질문 안에 숨은 질문을 넣지 마.
- “어떻게 할까?”처럼 넓게 던지지 말고 선택지를 좁혀.
- 추천 답은 반드시 포함해. 추천 없는 질문은 USER에게 일을 떠넘기는 거야.
- USER 답변 전에는 다음 질문으로 넘어가지 마.

Completion criterion: USER이 바로 답할 수 있는 단일 결정 단위여야 한다.

### 5. 답변을 압박하고 필요하면 꼬리질문한다

USER이 답하면 바로 수용하지 말고 한 번 검증해.

- 기존 코드와 충돌하지 않아?
- 나중에 마이그레이션이 어려워지지 않아?
- 보안/권한/개인정보 문제가 생기지 않아?
- 테스트 가능한 형태야?
- 실패했을 때 롤백 가능해?
- API나 데이터 모델을 너무 일찍 고정하는 건 아니야?

답이 탄탄하면 “좋아, 이 결정은 이렇게 기록할게” 하고 다음 질문으로 간다. 답이 모호하면 꼬리질문 1개만 한다.

Completion criterion: 결정 하나가 명확한 문장으로 기록되어야 한다.

### 6. 결정 로그를 유지한다

각 답변 뒤에 짧은 결정 로그를 누적해.

```md
결정 로그
1. <결정>: <이유/근거>
2. <결정>: <이유/근거>
```

결정 로그는 나중에 PRD, 구현 계획, 테스트 계획으로 바로 바꿀 수 있어야 한다.

Completion criterion: 지금까지 확정된 내용과 아직 열린 질문이 분리되어 있어야 한다.

### 7. Grill 종료 조건을 명확히 한다

다음 중 하나면 종료해.

- 핵심 리스크 질문이 다 끝났고 구현 계획으로 넘어갈 수 있음
- USER이 “여기까지, 이제 구현”이라고 명시함
- 답변이 막혀서 추가 자료/JD/코드/정책 문서가 필요함
- 설계가 위험하다고 판단되어 대안 방향을 제안해야 함

종료할 때는 요약해.

- 확정된 결정
- 남은 리스크
- 추천 구현 순서
- 구현 전 반드시 확인할 파일/테스트

Completion criterion: 다음 액션이 “구현”, “PRD 작성”, “추가 조사”, “설계 재검토” 중 하나로 정해져야 한다.

## Codebase Exploration Rules

- **질문 전에 검색해.** 파일명, 타입명, 엔드포인트, DB 테이블, 테스트명을 먼저 찾는다.
- **기존 패턴을 우선한다.** 새 추상화보다 기존 구조와 맞는지가 먼저야.
- **근거를 짧게 보여줘.** “찾아보니 X라서 Y를 묻는다” 정도면 충분하다.
- **파일이 없다고 단정하지 마.** 검색어를 바꿔 최소 2번은 시도해. 예: `billing`, `payment`, `invoice`처럼 도메인 동의어.
- **코드에서 확인 가능한 걸 USER에게 묻지 마.** USER에게는 제품 판단, trade-off, 의도처럼 코드가 말해주지 않는 것만 물어봐.
- **테스트를 설계 질문에 포함해.** 결정이 테스트로 검증 불가능하면 설계가 아직 흐릿한 거야.
- **마이그레이션과 롤백을 조기에 본다.** 데이터 모델/API 결정은 되돌리기 어려우니까 초반에 grill 해.
- **보안·권한·개인정보는 별도 리스크로 본다.** “나중에”로 미루지 마.

## Question Patterns

- “이 기능의 source of truth는 어디야? 내 추천은 기존 `X`를 유지하는 거야. 새 테이블을 만들면 동기화 문제가 생겨.”
- “이 API는 public contract로 고정할 거야, 내부용으로 둘 거야? 내 추천은 먼저 internal로 두고 사용처가 2개 이상 생기면 고정하는 거야.”
- “실패 상태를 사용자에게 노출할 거야, 조용히 재시도할 거야? 내 추천은 사용자 액션이 필요한 실패만 노출하는 거야.”
- “이걸 feature flag 뒤에 넣을 거야? 내 추천은 데이터 쓰기 경로가 바뀌니까 flag를 둬야 해.”
- “기존 데이터는 어떻게 마이그레이션해? 내 추천은 lazy migration보다 배치 + 검증 쿼리야, 이유는 읽기 경로 복잡도를 늘리지 않기 위해서야.”

## Common Pitfalls

1. **한 번에 질문 5개 던지기.** USER이 답하기 힘들고 결정도 흐려져. 무조건 하나씩.
2. **추천 없이 질문만 하기.** 그건 grill이 아니라 인터뷰 떠넘기기야. 항상 내 추천을 붙여.
3. **코드 확인 없이 사용자에게 묻기.** 파일에서 알 수 있는 건 내가 찾아야 해.
4. **사용자 답을 무비판적으로 수용하기.** 답을 받은 뒤 충돌·비용·테스트 가능성을 한 번 더 본다.
5. **구현 욕심으로 빨리 종료하기.** 핵심 리스크가 남았으면 구현으로 넘어가지 마.
6. **추상적인 철학 논쟁으로 빠지기.** 질문은 실제 파일, API, 데이터, 테스트로 연결되어야 해.
7. **결정 로그 없이 진행하기.** 나중에 왜 그렇게 했는지 잊히면 grill 실패야.
8. **반말이어도 무례하게 굴기.** 세게 묻되 USER을 깎아내리지 마. 설계를 공격하지 사람을 공격하지 않는다.
